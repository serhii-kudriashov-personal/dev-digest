# Eval Pipeline (L06) — implementation plan

## Task

Build SPEC-04: turn a judged finding into a frozen regression case in one click, run an agent's case set with arithmetic-only scoring (recall / precision / citation accuracy), compare two runs with an attributability warning, promote a historical agent version forward, and surface all of it on an agent Evals tab plus a cross-agent Eval Dashboard reachable from the left navigation.

## Requirements source

`specs/2026-08-18-l06-eval-pipeline.md` (SPEC-04) — AC-1…AC-50, NFR-1…NFR-12, `## Edge cases`, `## Workflows and contracts`, `## Untrusted inputs`. This plan implements those requirements and cites them; it does not define or amend them. The spec's own `## Open questions` 1–5 carry "assumption to proceed on" answers, and this plan takes each of them as written — see `## Answers taken`.

## Answers taken

Intake skipped by the caller (unattended run, single-agent mode, "state your own default assumption inline and proceed"). The requirements document exists, so nothing here is a derived requirement — but every line below is **my default, not the caller's decision**, and each is repeated under `## Risks & open questions`.

| # | Question the spec or repo left open | Default taken |
|---|---|---|

| A2 | Where run identity is stored, given `eval_runs` is keyed by `case_id` and carries no agent/version/model (`server/src/db/schema/eval.ts:22-36`) | A **new** `eval_set_runs` table holds the run identity and its own denormalised metric columns; `eval_runs` becomes the per-case detail row and gains `set_run_id`. | A10 | Promoting a version whose config already equals the live one (AC-38) | No new version is created; the response reports `promoted: false` and the UI states it is already live. AC-38's own verification promotes v6 while v7 is live, so it is unaffected. |

## Execution

**Single-agent**, as instructed: one `implementer` run, steps 1–17 in order, tests written in the same pass.

Honest cost of that choice, since the plan is 17 steps across two packages with a contract change and a migration: the same work in multi-agent mode would be `implementer` (1–9) → `plan-verifier` → `test-writer` (10, 17) → `architecture-reviewer` alongside the security review → `doc-writer`. In one context, the two risks the chain would have absorbed are (a) the `AC-N` set difference nobody computes, and (b) `pnpm arch` and `check-shared-sync.sh` being run once at the end instead of per step. Both are mitigated inside the steps: every step carries its own gate command, and `## Acceptance-facing checks` is written so a `plan-verifier` run can be added later without re-deriving anything. If the executor runs out of context, the natural split is **after Step 10** — the server is then complete, gated and tested, and `plans/<slug>.md` plus the changed-file list is the whole handoff for the client half.
