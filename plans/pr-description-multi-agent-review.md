## Title

Multi-Agent Review: agent picker, Configure run, Columns/Tabs comparison (SPEC-05)

## Summary

Implements SPEC-05 end to end: a reviewer can pick exactly which agents review
a pull request, launch them together, and compare their findings side by side
— including where they disagree — without leaving the product.

- **Agent picker on the PR page** replaces the old "run all / run one" dropdown
  (`RunReviewDropdown`, deleted). Same popover, now a multi-select with a
  live count and a link into the full Configure screen.
- **Configure run screen** (`/repos/:repoId/multi-agent`) — choose a PR, choose
  agents, see each agent's last run (duration/cost/summary) and a pre-run
  estimate before spending anything.
- **`multi_agent_runs` gets its first writer and reader.** The table has
  existed since an earlier lesson with nothing populating it; this PR adds the
  service, the repository, and the `multi_agent_run_members` link table that
  ties a set of agent runs together as one retrievable comparison.
- **Results screen, two modes** — Columns (one lane per agent, side by side)
  and Tabs (one agent at a time) — both reading the same run record, so
  switching modes never goes stale relative to the other.
- **Cross-agent grouping** — findings that name the same file with overlapping
  line ranges are grouped into one location, with every completed agent's
  stance shown (including "did not flag it," never a reason for it — the model
  is never asked why it stayed silent). A "Where agents disagree" filter hides
  locations every agent agrees on.
- **The existing run-trace drawer is reused whole**, promoted to a shared
  component so both the PR page and the Multi-Agent Review screen open the
  identical surface — same sections, same live-log/persisted-trace switch, no
  second implementation.
- **Accept / Dismiss / Turn into eval case** work from inside the comparison,
  reusing the shipped finding actions and the eval bridge. **Learn** is wired
  as an intent-only action (`findings.learned_at`) — no memory mechanics yet,
  by design (spec §Non-goals).
- **"Start new review" and "return to the last run."** Once a PR has a run,
  the screen defaults to showing it (not a blank form), and a `new=1` toggle
  plus a `localStorage`-remembered last PR let the left-nav entry point come
  back to where you left off instead of always prompting to start over.

## What changed, by area

### Server — data model (2 migrations, `pnpm db:migrate` required)
- `multi_agent_run_members` (new table): links an `agent_runs` row to a
  `multi_agent_runs` row, with `position` (preserves lane order) and a
  snapshotted `agent_name` (survives the agent being deleted later).
- `multi_agent_runs.head_sha` (new column): the PR's head commit at launch
  time, so staleness is computed at read time by comparing against the PR's
  *current* head — never stored as a stale boolean.
- `findings.learned_at` (new column): the "Learn" intent, nullable.

### Server — new `multi-agent` module
`server/src/modules/multi-agent/{routes,service,repository,helpers,constants}.ts`
- `POST /pulls/:id/multi-agent-runs` — start a run for a chosen agent set
  (own rate limit; each call fans out to N paid model calls).
- `GET /pulls/:id/multi-agent-runs` — a PR's runs, newest first.
- `GET /multi-agent-runs/:id` — one run's lanes, grouped locations and totals.
- `GET /multi-agent/agent-history` — every agent's last completed run, for the
  Configure screen's per-agent history and pre-run estimate.
- Reuses the existing `ReviewService.runReview` / `ReviewRunExecutor` for the
  actual agent fan-out — this PR does not touch execution, only grouping and
  persistence around it. Wired into `container.ts` as `container.reviews`
  (the sanctioned cross-slice channel) and registered in `modules/index.ts`.

### Server — `reviews` slice (small, additive)
- `FINDING_ACTIONS` gains `'learn'`; `POST /findings/:id/learn` records
  `learnedAt` via a new `setFindingLearned` repository method. `accept` /
  `dismiss` are unchanged.

### Shared contracts (both `server/` and `client/` vendored copies)
- `observability.ts`: `MultiAgentStartRequest`, `MultiAgentRunSummary`,
  `MultiAgentRunResult` (lanes, grouped locations, totals), `AgentHistoryRow`
  rewritten to the shapes the acceptance criteria require (previously
  scaffolded with zero consumers).
- `review-api.ts`: `FindingRecord.learned_at`.

### Client — new route and shared components
- `client/src/app/repos/[repoId]/multi-agent/` — the route: `MultiAgentView`
  (owns every query param: `pr`, `run`, `mode`, `trace`, `agent`, `new`),
  `ConfigureRunPanel`, `MultiAgentResults`, `AgentLane`, `DisagreementPanel`,
  `MultiAgentFindingCard`.
- `client/src/components/agent-picker/` — `AgentPicker`, promoted to a shared
  component from birth (used by both the PR header's popover and the
  Configure screen's inline agent block).
- `client/src/components/run-trace-drawer/` — the existing `RunTraceDrawer`
  and its `_components/` promoted out of the PR-detail route so the
  Multi-Agent Review screen can open the same drawer, unchanged, for any
  lane's trace.
- `client/src/vendor/ui/nav.ts` — new "Multi-Agent Review" entry in the left
  nav (`g m`).
- `client/messages/en/{runs,prReview}.json` — the comparison/trace copy that
  already existed unwired is now live; the strings that contradicted the
  shipped design (`"fan-out via p-queue"`, "Run all agents") are reconciled —
  execution is sequential, not parallel, and the estimate/header copy says so.

### Client — PR page
- `PrDetailHeader.tsx` — the old `RunReviewDropdown` is gone; the new
  `AgentPicker` popover is the only review-launch control, with a link into
  Configure run.
- `PrDetailView.tsx` — updated to the promoted `RunTraceDrawer` import path.

### This session's addition on top of the above
- **"Start new review" button** on the results toolbar (`?new=1`) — without
  it, once a PR had any run, the Configure screen became permanently
  unreachable for that PR (the "last run" fallback always won).
- **Last-PR memory** (`localStorage`, key `dd-multiagent-pr-<repoId>`) so the
  left-nav entry point — which carries no `?pr=` — returns to the last run
  viewed on this screen instead of an empty Configure form every time.
- See `client/INSIGHTS.md` (2026-08-25) for the underlying trap.

## Out of scope (by spec, unchanged in this PR)
- The review executor's fan-out stays sequential (no concurrent agents) —
  making it parallel is a separate change; this PR's estimate and copy are
  honest about that.
- `reviewer-core`, `agent-runner/`, `ci/` — untouched.
- Per-Agent Stats screens, memory-learning mechanics, "Reply to author" — not
  built; see spec `Open questions` 2–7.
